# Hermess Desktop 界面插件化与布局装配方案

第一期已在 **`v0.1.11` 开发分支**实现，全面自定义留到后续。本文记录第一期范围及后续设计。核对日期为 2026-11-10，实施前产品基线为 `fb313f2`，Hermes 基线以 [upstream.lock.json](../runtime/upstream.lock.json) 锁定的 `222b3748470c369050078ff3864100deb609918e` 为准。

## 0. 全阶段实施原则

**本方案所有阶段均以零 Hermes fork 改动为硬约束。** 保持 `runtime/upstream.lock.json` 和锁定源码不变，构建沿用原样归档的上游源码。新能力落在 Hermess Desktop 的前端、共享契约、Tauri/Rust 宿主，或现有插件扩展点内。涉及 Gateway 时只使用锁定版本已提供的协议和语义。

每个阶段开工前列明所需的 Hermes 能力与接收方证据。若锁定接口无法满足，先缩小该项能力的范围，保留桌面可实现部分。确实需要新增 Gateway 接口、改变现有语义或修改 Hermes 内部生命周期的事项单列为独立缺口，本方案的阶段交付不依赖它。 [仓库约束](../AGENTS.md)

## 1. 用户要能做什么

**第一期先明确 Hermess 能识别哪些插件定义，以及各类界面贡献如何接入。** 开发者可以按同一份契约声明插件身份、入口和页面，使用现有 SDK 注册组件，沿用现在的安装、启停和加载流程。第一期保持当前产品页面结构和默认位置。

**后续再评估全面自定义。** 用户可以自己开发插件，从本机导入或从 Git 和市场安装，然后选择组件放在哪里。应用提供默认布局，允许每个 Profile 选择布局预设、移动组件、调整顺序、隐藏组件和替换内置实现。

目标范围覆盖主导航、页头和工具栏、聊天与编程工作区、消息展示、输入区、左右面板、会话、文件、记忆、任务、专家、模型、设置及命令入口。实施时建立界面清单，逐项标记支持的新增、替换、排序和隐藏操作。普通聊天、编程聊天、群聊及独立聊天窗口分别列出，避免只迁移主窗口的一条路径。

界面能替换到什么程度，由各区域的用途决定。例如右侧栏允许多个标签，输入区始终只有一个生效的输入组件。发送、审批、权限、凭据、运行时进程和故障恢复仍由宿主管理。相应界面可自定义，操作结果由原有业务能力决定。

## 3. 插件定义与后续装配设计

```text
内置功能、Dashboard 兼容适配器、新版插件 → 组件注册表
默认布局或 Profile 布局 → 布局校验 → 按组件 ID 组装 → React 区域渲染
界面交互 → 宿主能力 → 原有控制器 → DesktopApi / Tauri / Hermes
```

### 3.1 第一期的插件定义

- **复用已有清单。** 从 `dashboard/manifest.json` 及现有 Dashboard 响应收敛插件身份、名称、版本、入口 JS、可选 CSS、页面路由和覆盖声明。继续使用现有 Rust 清单校验和前端注册流程。已安装插件按原有清单读取，无需用户改包或重新安装。
- **区分声明与实际注册。** 清单描述插件提供什么。`register()` 和 `registerSlot()` 的执行结果决定有哪些页面和插槽组件可以渲染。清单里的 `slots` 作为说明，不能用它推定组件已经注册。错误信息区分清单无效、资产加载失败和组件未注册。
- **按现有 Profile 边界收敛状态。** 定义和注册结果跟随当前 Profile 及 Dashboard 运行时，沿用现有启用和回收流程。保留现有独立页、隐藏页、覆盖和插槽行为。以一个已有页面和一个现有插槽样例验证，首期只暴露已支持的位置。
- **提供可复制的开发样例。** 样例用现有 SDK 注册独立页面与 `chat:top` 插槽，提供清单、可直接加载的脚本、本地检查和 Git 安装步骤。独立插件运行环境、全新包格式和完整开发工具链按后续使用场景评估。 [Dashboard 插件开发样例](../examples/dashboard-plugin/README.md)

### 3.2 后续的区域与组件注册

- **区域**由宿主定义稳定 ID、输入上下文、默认组件和数量规则。拟议的 `chat.right` 是多项区域。`chat.composer` 是单选区域，始终解析出一个可用输入组件。
- **组件定义**具有命名空间 ID、显示名称、可放入的区域、所需 SDK 版本和使用的宿主能力。内置组件和插件使用同一套定义。版本升级尽量保留 ID，改名时提供显式迁移。
- **组件实例**具有独立实例 ID，用于在同一区域内排序和保留允许重复组件的各自配置。定义 ID 表示组件类型，实例 ID 表示布局里的那一个位置。
- **命令和消息渲染器**使用各自的类型契约。消息渲染器由宿主按消息类型选择，保留默认文本渲染。命令调用复用原有权限和执行路径。

### 3.3 后续的布局配置与切换

进入布局自定义阶段后，先采用命名区域和预设，在 React 中使用现有分栏和标签组件。任意分栏、嵌套标签和跨区域拖拽需要时再增加布局树。两种布局形态共用同一套组件定义和实例 ID。

布局配置存到产品自己的偏好存储，作用域使用产品数据根内的 Profile 身份，Gateway epoch 只用于运行时状态隔离。当前 Profile ID 可改名。如果沿用现有 ID 作为键，改名成功后要迁移布局键，删除 Profile 后清理其布局，防止重建同名 Profile 时读到旧配置。首批由主窗口修改布局，多窗口共同编辑前再增加写入版本校验。布局独立保存配置版本、区域、实例 ID、组件 ID、顺序及允许的展示参数。配置不携带组件源码、会话正文或凭据。布局配置版本与插件 SDK 版本独立演进。 [Profile 改名和删除入口](../apps/frontend/src/features/profiles/useProfiles.ts)

装配顺序为「产品默认布局 → 用户选中的预设 → 当前 Profile 的覆盖」。区域未设置时继承，显式空列表表示隐藏可选区域。切换时先解析候选布局并校验区域、组件版本与能力，再应用。必需区域缺失时回退内置组件，可选区域缺失时略过该项并提示原因。保留已保存的用户选择，便于重新启用插件后恢复。恢复默认时明确选择产品默认布局，并清除当前 Profile 的自定义覆盖。「恢复默认」和「回到旧版覆盖规则」是两个独立操作。

### 3.4 后续的状态与生命周期

| 状态 | 所属位置 | 切换布局时 |
| --- | --- | --- |
| 当前会话、流式事件、待审批、草稿和待发送附件 | 聊天控制器及当前会话作用域 | 复用同一控制器，替换组件重新读取快照 |
| 文件标签、终端句柄和后台任务 | 工作区控制器及登记的资源所有者 | 仅移动界面时沿用原资源。替换插件时结束旧实例及其登记的资源。宿主共享资源和其他插件的资源按自身生命周期运行 |
| 区域尺寸、组件顺序和已选预设 | Profile 布局配置 | 应用布局变更，重启后恢复 |
| 悬停、弹层和组件内部临时状态 | React 组件 | 随组件生命周期变化。需要跨区域恢复的状态经显式能力保存 |

React 按组件在渲染树中的位置保存局部状态。跨区域移动时，稳定 ID 本身无法承诺保留内部状态。先将必须持续的业务状态放到对应控制器，再迁移 UI。验证右栏装配时，可保持原工作区资源所有者持续挂载，只切换右栏标签内容。开放输入区替换时，宿主仍负责附件拖放订阅和动作路由，切换前后应各只有一个生效的输入处理方。 [React 状态保留规则](https://react.dev/learn/preserving-and-resetting-state) · [当前聊天拖放订阅](../apps/frontend/src/features/chat/useChatController.ts#L432)

### 3.5 后续插件切换时先结束旧实例，再启动新实例

装配器比较当前与目标布局，找出需要替换的插件实例。单纯调整同一个实例的位置和顺序只更新布局。由桌面宿主独立管理的新版插件，替换时执行「结束旧实例 → 确认退出 → 启动新实例」。已安装或已启用的插件可以处于待启动状态。互斥区域里的新实例在旧实例退出后才激活。

| 检查结果 | 用户看到什么 | 切换行为 |
| --- | --- | --- |
| 旧实例空闲 | 显示切换进度 | 点击切换后直接结束旧实例，再启动新实例 |
| 旧实例有占用 | 列出旧插件名称、受影响的区域和资源，例如「插件 A 有 1 个打开的终端。切换会关闭该终端并启动插件 B」 | 提供「结束并切换」和「取消」。取消保留原实例和布局 |
| 归属或退出状态无法确认 | 显示具体资源及原因 | 暂停切换，允许重新检查或取消 |

切换前只校验目标插件的清单、版本和资源文件。确认结果绑定旧实例、目标插件、Profile、连接代次和已展示的资源 ID。开始结束前再核对占用。发现新的占用或归属变化时，重新展示清单。终端已打开只说明会话仍存在，有前台进程证据时才显示「命令正在运行」。未保存的用户数据按对应组件的保存规则处理。

确认后由宿主停止旧实例接收新操作，撤销其回调和订阅，销毁其运行环境并终止它登记的产品进程树。结束范围按实例归属核对。如果一个实例同时服务多个区域，提示列出所有会受影响的区域。Hermes Gateway、宿主共享聊天、其他插件、其他 Profile 和系统应用各自独立运行。 [产品进程管理约束](../apps/desktop/AGENTS.md)

退出确认后才启动新实例。新实例完成注册并达到可用状态后，保存目标布局。旧实例结束失败或超时则保留现有布局配置，显示已结束和待确认的资源，新实例保持待启动。若旧实例已退出而新实例启动失败，显示内置回退组件，并提供重试新插件或重新启动旧版本的操作。已被终止的任务按其实际状态显示。

现有 Dashboard 插件的脚本注入主 WebView。卸载 React 组件、删除脚本标签和撤销现有请求桥只能清理宿主掌握的部分。新版 UI 插件的独立运行环境由桌面宿主创建和销毁，后台进程由产品共享进程管理器登记并终止其子进程树。旧 Dashboard 插件保留兼容入口，界面移除与运行环境退出分别显示。旧插件适配现有布局入口后，仍按其原有运行生命周期管理。 [现有脚本注入及清理](../apps/frontend/src/features/dashboard-plugins/DashboardPluginHost.tsx#L489)

当前终端关闭命令先移除终端记录，再等待受管进程树结束。首次关闭失败后，重复调用可能因为记录已不存在而返回成功。因此，实施时需要能确认原进程树已经退出的结果，再将该资源标记为已释放。直到完成这项验证，失败后无法确认状态的终端显示「结束状态未知」。 [Rust 终端关闭实现](../apps/desktop/src-tauri/src/panel_terminal.rs#L297)

### 3.6 兼容与权限

- 旧 Dashboard 独立页继续沿用现有入口。未采用新布局的页面保留旧 `tab.override` 和插槽规则。对某个页面显式启用新版布局后，该页由布局装配器决定内容，旧插槽通过兼容适配器只接入一次，旧整页覆盖在该页暂停生效。回到旧布局时恢复原有覆盖行为，插件的启用状态保持可独立管理。主导航与路由打开两个入口都要验证，避免分别选中不同的覆盖组件。
- 第一期沿用现有 Dashboard 的 WebView 执行模型。声明能力、过滤 API 或捕获 React 渲染异常，都不足以隔离任意脚本。后续如果引入独立运行环境，先用受信样例验证消息桥和退出。旧 React 组件不能凭注册接口直接迁入独立环境。面向未信任来源开放运行前，单独验证安全隔离能力。
- 带 Python 后端、Agent 工具或 Gateway 钩子的现有 Hermes 插件继续使用原启停语义。新版布局切换只管理客户端实例。锁定 fork 的 `hermes_cli/plugins_activation.py` 中，`gateway_reload_hint` 明确说明已接入平台适配器的回调可能在重载后继续存活。Gateway 内彻底热卸载属于独立缺口，不是本方案的验收条件。
- 新的能力句柄绑定当前 Profile、会话及连接代次。宿主校验请求作用域和调用权限。插件停用、Profile 切换或连接退役后，旧句柄与订阅失效。
- 宿主保留可恢复默认布局和停用插件的入口。局部渲染错误由区域边界处理。无法进入主界面时，应有在加载扩展脚本前生效的恢复方式。两类故障分别验收。

## 4. 后续用户开发工具

第一期提供基于当前清单和 SDK 的最小示例，用户仍可用现有入口安装。下面是后续开发工具的候选范围。

1. 从「插件开发」创建模板，先提供独立页面、区域组件和替换组件的最小示例。首个样例用 React 和 TypeScript 开发，继续采用清单、入口 JS 和可选 CSS 的交付结构。新版清单明确标识桌面 UI 插件，入口由桌面独立运行环境加载。旧 `dashboard/manifest.json` 继续用于 Hermes 兼容路径。
2. 开发者在本地编辑源码，构建工具监听变化。Hermess 关联开发目录，在测试 Profile 预览构建产物，报告清单解析、SDK 版本、组件注册及渲染错误。首批支持显式重新加载，自动热更新根据验证结果再引入。
3. 从本地导入时，先校验入口文件、路径边界及插件 ID，拒绝通过链接指向包外的文件。将已构建的包写入临时位置，校验通过后替换产品管理目录中的版本并记录来源。关联开发目录用于调试，导入快照用于正常使用。新版 UI 包从 Git 或市场获得后，也进入桌面端同一条校验和安装路径。新版 UI 安装只处理桌面清单和界面资产。Hermes 插件的 Python 依赖安装、后端加载和启用仍走现有 Hermes 入口。同一 Profile 内，同一个插件 ID 只装配一个已选版本。不同来源遇到同名时显示冲突，要求通过显式更新选择新来源。失败的导入或更新保留上一次可用版本。
4. 用户在布局中选择组件位置，预览、应用或恢复默认。发布时共享仓库和固定版本，接收方安装后自行决定放置位置。
5. 这条链路稳定后，再提供类似 Creator Mode 的入口，由 Agent 使用相同模板与 SDK 生成插件，并交给用户在测试 Profile 预览和启用。

| 阶段 | 实施范围 | 退出条件 |

## 6. 验收与记录

- **第一期验收**。沿「安装或启用 → Gateway 返回原有清单 → 前端加载 → SDK 注册 → 页面或插槽展示」核对。检查同一 Profile 的插件启停、已注册状态和错误提示。用两个 Profile 验证切换后旧贡献不会留在新作用域。第一期完成以现有插件兼容和定义可用为准。
- **后续验收**。下面的布局切换、占用、进程退出和本地导入场景随对应功能验收。
- **前端行为**。以「Agent 正在流式回复时切布局」为主用例。断言同一会话继续接收事件，草稿和附件保留。验证插件注册失败、渲染异常、停用、卸载、Profile 切换、Gateway 重连和重启恢复。
- **占用和结束**。验证空闲切换、有占用并确认、取消、状态未知、结束超时和新插件启动失败。用宿主事件核对旧实例退出先于新实例启动。模拟确认后出现新占用及多项结束只有部分成功，核对布局配置和结束清单，并验证另一个 Profile、宿主共享会话与产品外进程保持原状态。
- **安装与作用域**。用两个隔离 Profile 和合成插件验证本地导入、Git 安装、同名冲突、更新失败回退与卸载。读取产品管理目录中的实际结果，并检查原有 Hermes 安装与另一 Profile 的数据边界。验证改名后布局可读，删除并重建同名 Profile 后使用默认布局。
- **生产协议**。新增或修改跨层接口时，从 React 调用追到共享契约、Tauri、Rust 及锁定 Hermes 接收方，验证成功和关键拒绝。浏览器模拟只记录为界面验证。
- **零 fork 核验**。各阶段确认锁文件和上游源码无差异，运行 `pnpm verify:upstream`，并核对新增能力是否仅通过现有 Gateway 协议接收。确需改动上游语义的事项移入独立缺口清单。
- **平台与日志**。Windows WebView2 和 macOS WKWebView 分别验证目录选择、加载、重启、终端结束和恢复。用同一操作标识记录占用检查、用户选择、结束结果、切换和回退。凭据、用户消息和本机敏感路径留在日志之外。

第一期在 Windows 上已通过前端类型检查、生产构建、架构与契约检查、上游锁定检查、Node 和 Rust 测试。Windows 原生 WebView2 调试窗口连接锁定 Gateway，验证非法安装地址拒绝、本机 HTTPS Git 安装并启用、样例页面交互和聊天插槽、既有 Achievements 入口注册、两个 Profile 的贡献与资产隔离、停用与恢复、重新扫描加载修改后的脚本，以及卸载取消和确认。结果通过安装记录、文件与资产路由回读。Chrome 模拟桌面宿主另验证了入口、样式加载失败和脚本未注册提示。macOS 原生窗口、安装包及后续布局装配尚待验收。

## 7. 实施前需要确认的事项

- **后续安装**验证桌面端能否用同一套包校验管理本地导入和 Git 下载的构建产物，同时回归现有 Hermes 插件的安装、发现和启停。
- **后续切换**分别验证旧 `registerSlot()` 的布局兼容和新版插件的独立退出。在双平台核对进程树退出及启动时绕过故障插件的恢复入口。
