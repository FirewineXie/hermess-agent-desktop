# Bot Room：独立插件讨论与需求验证

状态：**讨论草案，尚未立项、未排期、未实现，不纳入 ROADMAP。** 最后整理：2026-11-06。

用户已明确：目前没有真实用户提出“让自己的 Bot 与另一个人的 Bot 一起完成任务”，主要是产品设想。下文保留讨论方向、现有代码证据与待验证问题，不代表决定开发完整功能。只有明确决定实施并确认范围后，才将确定要做的部分登记到路线图。

## 1. 先验证什么价值

核心问题：**什么任务必须用到另一个人的 Bot，而不是自己已有的几个 Bot、共享文件或直接找对方？**

可能有价值的场景如下，均为需求假设，尚无用户案例或留存数据支持：

| 场景假设 | 对方可能具有的独有能力 | 需要验证的收益 |
| --- | --- | --- |
| 两个开发者联合排查问题 | 不同代码库、运行环境和测试工具 | 是否减少人工转述与反复复制结果 |
| 不同岗位共同完成任务 | 各自维护的资料、业务上下文和工具权限 | 是否比共享资料或直接问人更省事 |
| 调用另一台机器上的能力 | 特定软件、设备或本地执行环境 | 是否有真实、重复发生的远端执行需求 |

“几个 Bot 一起聊天”本身不足以证明需要跨主人、跨 Gateway 的产品。双方安装插件、邀请与审批、同时在线以及切换到桌面房间，都会增加使用成本。需要验证节省的工作能否覆盖这些成本，不能把兴趣、点赞或一次演示当作持续使用。

## 2. 讨论中已经明确的方向与约束

以下约束用于后续评估，不代表功能已获实施批准：

- **独立插件交付。** 参考 OpenViking 的独立包交付方式，可单独安装、配置、启停和升级；不把全部业务写进 Hermess Desktop 或 Hermes fork。OpenViking 的记忆接口不等于房间接口，不能直接套用。
- **优先复用 Hermes。** 先复用已有房间、会话、成员执行、工具审批和日志，只补经验证缺失的部分；不默认重写一套房间系统。
- **首版设想只考虑桌面入口。** 不接入飞书等外部聊天渠道。
- **主 Bot 调度不是必需条件。** 不增加必须的主 Bot、首轮主 Bot或最后强制汇总；需要总结时由用户明确提出。
- **跨主人授权。** 两个人各自管理 Gateway，Profile 对应可独立启用的 Bot。保留“邀请密钥 → 申请发现 → 主人选择可见 Bot → 申请指定 Bot 入房间 → Bot 主人批准”的两次审批意图；工具审批仍由执行方主人控制。
- **连接目标。** 每台 Gateway 配置一次共享连接，各 Profile 独立启用；拟采用经身份认证的端到端加密，中转只转发在线密文，不保存消息或离线队列。参与方可以保留获准的本地记录，具体接入方式尚待验证。
- **验证规模从小开始。** 若决定开展原型验证，先用两台 Gateway、各一个 Bot 完成一项真实任务，不先扩展多成员自动讨论。
- **当前只改文档。** 不修改产品代码、fork 或锁文件；尚未证明完整目标可以零 fork 改动实现。确有宿主缺口时，按仓库规则提交证据、拟改范围与影响，另行取得明确审批。

## 3. Hermes 已有能力与复用边界

本节依据产品锁定的 Hermes fork 提交 `882037eb8745b505db438217513c4c94f95c93c1`，不是对其他版本的承诺。当前只完成静态源码核对，未跑跨 Gateway 原型。

| 能力 | 已核实的事实 | 尚待验证的边界 |
| --- | --- | --- |
| 房间与日志 | 已有 `groups.create/send/state/log` 及房间执行服务 | 插件能否通过当前产品实际入口操作同一套房间服务 |
| 跨 Gateway 成员 | 已有 peer grant、撤销、注册、日志副本及 peer transport 代码 | canonical 接口未完整暴露 peer 管理与复制方法，能力响应为 `room_link.enabled=false`；底层实现不等于生产入口可用 |
| 现有 RoomLink | 当前实现支持 direct 连接 | 公共在线密文中转不是现成能力；需验证能否通过受支持扩展接入 |
| Bot 执行与审批 | 已有会话、模型、工具执行及权限机制 | 跨主人请求必须保留接收方的权限判断，不能把远端请求者变成本机工具审批人 |
| 插件交付与接入 | 已有工具、命令、hook、状态、生命周期与插件 HTTP API | 按 Profile 加载不等于 Gateway 单实例；host 隔离模式也可能限制能力 |
| 桌面入口 | 产品已调用当前 Gateway 的房间接口 | 跨主人身份、审批及远端状态是否能沿用当前契约，需要逐项追踪生产调用链 |

优先职责划分：Hermes 负责房间与执行的权威状态；插件补足经确认缺失的邀请、跨主人授权和连接适配；桌面负责入口与必要展示。若需要对既有授权包装产品流程，应明确两者的映射与撤销规则，不复制一套互相冲突的审批状态。

现有 canonical 与 legacy 房间服务的登记路径并不相同。不能因为 legacy 有某个方法，就假定它能操作产品当前创建的房间；必须验证同一房间的创建、授权、投递、结果与恢复都落到正确接收方。

## 4. 三轮、十条限制

已核实：`gateway/hosted_room_discussion.py` 中 `MAX_DISCUSSION_ROUNDS = 3`、`MAX_DISCUSSION_MESSAGES = 10` 限制的是**一条用户消息触发的一次自动讨论**，不是整个房间最多聊三轮或只能保存十条消息。十条额度计入该讨论的 Bot 消息；新的用户消息会启动新的讨论预算。

但该限制确实可能影响需要持续交接的协作。当前查明的代码还包含 `r[0-2]` 恢复坐标、轮次校验，以及策略检查点的 64 条活跃事件限制，不能只改两个常量就声称支持任意轮数。尚未找到已公开可配置的讨论预算入口。

处理顺序：

1. 用真实任务确认需要的是用户持续聊天、单次自动讨论超过 3/10，还是两者都需要；不能把它们混为一谈。
2. 优先验证现有房间与明确 @ 的协作方式。现有基础调度不要求主 Bot，无 @ 的用户消息可能唤醒全体成员，需验证是否符合目标体验。
3. 若已确认的任务确需更长自动讨论，再验证预算扩展、停止、恢复及费用控制。可配置额度目前是需求，尚不是可用能力。
4. 不通过伪造用户消息或自动发送“继续”绕过额度，也不提前承诺无限轮转。

此前“由插件自建房间并绕开内置 Discussion”的写法不再作为默认方案。只有在既有房间接口经验证无法满足已确认需求时，才比较最小宿主扩展与插件自管房间的代价，并重新确认方向；不能以插件形式交付为由，默认重复实现 Hermes 已有能力。

## 5. 技术问题清单，尚非开发任务

需求验证通过并决定继续后，再核实以下问题：

- **合法执行与结果闭环。** 已有房间或插件 API 能否完成目标 Profile 的首次授权、消息接纳、结果查询、停止和恢复。`ctx.inject_message` 受 Profile、会话与授权约束，不能凭空建立任意 chat；入队回执不等于执行成功，`post_message` 也不是任意会话发送接口。
- **共享连接生命周期。** 插件按 Profile 加载，部分实例可能位于不同 host 进程；先验证现有生命周期与连接机制。是否需要插件包提供伴随服务尚未决定，不能靠模块全局变量或强制启用某个 Bot 保证唯一连接。若引入产品自有进程，必须接入共享进程管理器并回收子进程树。
- **两次审批与撤销。** 邀请只能申请发现，不能携带 Gateway 管理凭据；主人只批准指定 Bot 和指定房间，模型输出不能批准。成员或权限变化、禁用插件、撤销授权、旧审批卡与请求重试应有明确处理。
- **消息与在线边界。** 复用现有事件顺序、身份和去重能力，只传递允许的房间操作，不透传任意管理 RPC。中转不离线排队；目标离线应明确反馈。已接纳任务断线后的结果补取与重新授权需验证，不能盲目重跑任务。
- **桌面与部署。** 验证插件管理/API/页面在目标 Profile 隔离模式下可用，不默认所有插件都支持 WebSocket。核心插件独立部署是目标，尚未证明可以脱离 Hermess Desktop 完整运行。
- **平台与日志。** 分别考虑 Windows/macOS 的凭据存储、本机通信、路径、进程树、托盘退出、安装与卸载。日志关联同一次任务的开始、状态、结果及清理，不泄露凭据或消息正文；单平台验证不代表双端验收。

优先使用公开接口，不依赖私有对象或 monkey patch 作为长期方案。若发现缺口，先记录接收方的实际接受或拒绝结果，再决定是否提出通用宿主扩展；不为未经验证的假设增加兼容层。

## 6. 建议的低成本需求验证

以下是待采用的验证建议，不代表已招募用户或已安排开发：

1. 找 3–5 对本来就有协作任务的试用者，每对先说明现有做法、麻烦之处和对方 Bot 的独有能力。
2. 先做访谈或人工辅助演示；若能找到真实场景，再确认最小原型范围。原型只需让一个 Bot 提出任务、对方授权的 Bot 执行并返回结果，不先完成插件市场发布或复杂房间界面。
3. 对照原有方式记录任务是否完成、人工转述次数、总用时、模型消耗、审批与离线造成的中断。
4. 观察用户是否主动发起第二次、第三次任务，以及是否愿意邀请真实协作者；一次尝鲜不算需求成立。

可考虑将“至少两对用户完成真实任务后主动再次使用，并能说明节省了什么工作”作为初步继续条件。这是本次讨论提出的实验标准，不是市场统计，也未获确认为固定指标。

若用户仍更愿意传文件、直接找人，或任务根本不依赖对方的独有能力，应缩小或搁置方向。若出现重复使用，再由用户明确决定是否实施、范围与版本，届时才更新 ROADMAP。
