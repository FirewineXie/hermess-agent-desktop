# 编程模式与 Codex App Server 接入方案

日期：2026-11-08。

状态：用户已确认开始实现，当前在 feature/v0.1.10 开发分支实施；功能尚未完成验收。实施进度和实际证据见 [实施记录](codex-programming-implementation.md)。

第一版范围已收敛：仅支持 Responses API 直连，不做 Chat Completions 协议转换；模型连接使用 AES-256-GCM 加密，每个客户端安装实例独立生成随机密钥。保留统一启动、全部模型入口、Shell 与状态目录隔离和换密钥恢复规则。已选择自动解锁：主密钥保存在产品私有目录并限制文件权限，不使用系统凭据管理器；此方式不能防止同一操作系统用户下的恶意程序读取。

## 1. 已确认的产品要求

1. 提供“编程模式”，底层使用 Codex App Server。产品正常使用界面不称其为“Codex 模式”；第三方许可证与必要来源说明保留真实名称。
2. 全局编程配置只有一份，所有 Hermess Profile 共用；配置内支持多个模型提供商，每个提供商保存地址、密钥与多个模型。每个编程会话的历史、项目目录、线程与执行状态独立。
3. 第一版仅支持标准 Responses API，标准请求路径为 `/v1/responses`；App Server 直连模型代理，不增加本地模型 Proxy，不额外转发模型 SSE，不支持仅有 `/v1/chat/completions` 的端点。
4. 代理地址、API Key、模型名称由客户端使用 AES-256-GCM 加密保存，每个客户端安装实例使用独立随机密钥；不使用系统凭据管理器保存这三项信息。
5. 其他编程运行配置由产品独立的 Codex 配置文件管理。客户端将需要展示的配置具象化为控件，直接读写对应字段，不另存一份运行配置。
6. Codex 配置文件中的模型连接与认证字段不得成为有效来源。启动适配层确保进程不采用这些值，并定时检查；不能要求用户解决两份配置冲突。
7. 不影响用户个人 Codex 的安装、配置、认证、历史、插件和运行中的进程。
8. 优先复用锁定 Hermes 的现有 App Server 能力，不直接打开会修改个人配置的迁移流程。未经另行明确审批，不修改 Hermes fork。

### 1.1 多提供商与 Profile 同步（2026-11-08 确认）

- 设置交互沿用 Profile 模型提供商：卡片列表、新增/编辑配置弹窗、独立模型列表编辑弹窗。模板下拉共用 Profile 的 API 密钥/自定义端点选项，不另设国内/海外按钮，不加入个人 Codex 登录流程。模板不代表已验证兼容。
- 提供商保存或从 Profile 同步时，由桌面后端对每个模型请求 Responses SSE，验证受约束的函数调用及工具结果回传；任一步失败或超时均不发布新配置。验证会向所填端点发送两轮小请求，可能消耗供应商额度；它不证明图片能力、所有工具或长上下文均兼容。
- Profile 同步先选择 Profile，再选择其中的提供商，预览地址及完整模型列表；复制所选提供商的静态 API Key 连接和已配置模型列表，不固定读取主模型。通过锁定 Hermes 的配置解析和提供商解析读取所选产品 Profile；OAuth、命令取密钥、额外认证头不支持复制。密钥经后端私有管道进入全局加密存储，不回显前端。同步是独立副本，原 Profile 后续变化不会自动覆盖编程配置。
- 提供商列表保存在唯一有效的 `connections.enc`。旧单连接按原模型身份导入，首次写入后清理旧文件；新目录有效时旧文件和旧保存入口不能覆盖它。仍用 AES-256-GCM 与安装实例独立随机密钥；`config.toml` 管理思考强度等允许选项。
- 聊天输入框按提供商分组选择模型。已有会话切换模型会新建会话，保留原历史和未发送内容；运行中禁用切换。会话绑定模型身份，修改地址或模型 ID 会生成新身份，旧会话保留历史但不能继续向新连接发送；只换密钥保留身份。
- 保存期间校验在状态锁外执行，停止任务保持响应；发布时复核配置修订和无运行任务，避免并发修改覆盖。删除提供商保留会话历史。错误、超时、验证阶段和最终结果记录安全日志，不记录密钥或模型响应原文。

产品锁定 openai/codex 的 GitHub 正式 tag `rust-v0.167.0`，平台归档、大小与 SHA-256 记录在 `runtime/codex.lock.json`。默认安装包不自带，用户在编程设置页下载；使用完整官方运行包中的 `codex app-server`，保留沙箱与命令执行辅助程序。仍须逐平台核实其协议和配置语义。不得将本机个人 Codex 版本或最新在线文档自动视为产品的版本契约。

### 第一版支持范围

| 项目 | 第一版决定 |
| --- | --- |
| 模型协议 | 标准 Responses API，使用 `/v1/responses`；不提供协议切换选项 |
| 模型连接 | 用户配置的 Responses 兼容代理；不限定模型品牌，以实际协议与工具能力验证为准 |
| 模型选择 | 客户端管理提供商及其模型，聊天输入区按提供商分组选择；模型 ID 手动添加，不要求模型发现接口 |
| 数据链路 | App Server 直接接收模型流；首版按固定版本验证 HTTP/SSE，关闭该 provider 的 WebSocket 尝试 |
| 编程能力 | 独立会话、项目目录、流式进度、工具调用、审批、停止与恢复；图片输入须验证模型和代理支持 |
| 客户端加密 | AES-256-GCM，每安装实例独立随机密钥；主密钥保存在产品私有目录并限制文件权限，自动解锁 |
| 不支持 | 仅有 Chat Completions 的端点、本地协议转换 Proxy、自动协议回退及第二套 Agent 执行引擎 |

第一版不实现外部网关部署或内置转换器。用户若自行使用提供 Responses 接口的外部网关，客户端将其视为普通 Responses 端点，仍须完成兼容性验证，不因网关声称支持而自动通过。后续支持 Chat Completions 的转换方案只作为另行讨论的候选，不列入本版交付范围。

## 3. 架构与职责

```text
Hermess 前端
  选择编程模式、配置模型、发送文字/图片、展示进度与审批
          │ 宿主能力契约
          ▼
Hermess 桌面适配层 / Rust
  客户端加密存储、配置过滤、会话归属、进程生命周期
          │ 必要的私有启动与通信链路
          ▼
App Server 会话客户端 → 产品独立的 Codex App Server
                           │ 使用客户端指定的地址、密钥与模型
                           │ HTTPS / 模型流式响应
                           ▼
                       用户配置的模型代理 → 模型
```

| 职责 | 所有者 |
| --- | --- |
| 模型连接信息的持久化、解密、选择和注入 | Hermess 客户端 |
| 运行配置的持久化 | 产品独立的 Codex 配置文件 |
| 运行配置的图形化编辑 | Hermess 客户端 |
| 向模型代理发起请求与接收模型流 | App Server |
| 编程上下文、压缩与工具执行循环 | App Server |
| 会话与线程对应关系、历史展示、审批交互和停止入口 | Hermess 客户端 |
| 产品进程启动、登记、清理与退出 | 共享进程管理器 |

不在客户端增加另一套上下文压缩或编程 Agent 循环。复用会话客户端不意味着必须使用现有 Profile 的全局运行时开关，也不意味着完整继承其迁移、认证和插件装配行为。

产品适配收敛为三个模块，不另建通用配置平台：

| 模块 | 职责边界 |
| --- | --- |
| 客户端加密配置 | 保存与解密地址、密钥和模型，区分连接身份与凭据修订 |
| 统一启动适配层 | 一次性构造有效配置、环境、目录与模型参数，经共享进程管理器启动并校验结果；恢复线程也经过该边界 |
| Codex 配置编辑器 | 读写允许的运行选项，保留其他合法内容；一个全局定时检查发现异常修改 |

所有编程进程使用同一启动入口，不分别在新建、恢复、测试连接等入口拼装过滤逻辑。

## 4. 两类配置与唯一数据来源

### 4.1 客户端加密的模型连接信息

仅客户端持久化以下三项：

- 模型代理地址。
- API Key。
- 模型名称，即代理实际支持的模型 ID。

三项按全局编程配置保存，不复制到各 Profile，不写入 Codex `config.toml`。前端保存后只得到必要的展示数据及“密钥已配置”状态，不回读完整密钥。

地址与模型名称需要在设置界面展示时，由宿主按用途解密后返回；不把整个加密存储或解密密钥交给前端。API Key 采用只写不回显的交互，替换、清空与保留的语义须明确区分。

加密参数与实例隔离规则已确定：

- 使用 AES-256-GCM 认证加密，同时校验密文完整性；不以“最强加密”等不可验证描述代替具体算法。
- 首次配置时，通过系统密码学安全随机源生成 256 位密钥；不得从机器名、MAC 地址、安装 ID 或其他可预测标识直接推导。
- 每个客户端安装实例独立生成密钥，不跨客户端共用，不按 Profile 或聊天会话重复生成。产品正常升级保留原密钥，不因升级产生解密中断。
- 同一密钥下不得复用 nonce，采用成熟实现推荐的生成方式；并发保存、失败重试和恢复流程都须验证。文件格式保存必要的版本、nonce、密文与认证标签，不保存明文连接信息。
- 优先复用仓库已有 `aes-gcm` 依赖，不自行编写密码算法；算法选择不代表现有草稿已经符合加密要求。
- 客户端主密钥与用户填写的代理 API Key 是两种不同凭据；替换 API Key 不更换主密钥，不影响同连接的线程恢复。
- 默认不把主密钥随普通配置或支持导出分发给其他客户端。仅拷贝密文不能默认跨客户端解密；密钥丢失或密文校验失败时明确报错，不自动生成新密钥覆盖原数据。跨客户端迁移不纳入第一版。

**主密钥的生成来源已明确，保存保护与解锁方式尚未确定，属于实施前必须明确的事项：**

- 不使用系统凭据管理器，不能沿用此前 keyring 草稿。
- 不在源码或程序中硬编码固定解密密钥。
- 若选择自动解锁，必须如实说明本机密钥材料及其访问权限能提供的保护边界。
- 若选择用户主密码解锁，需定义启动解锁、锁定、忘记密码及重新配置流程。
- 加密格式须支持完整性校验、版本标识与原子更新；不得自行设计密码算法。

“文件加密”不意味着程序运行时无需解密，也不意味着能抵御已控制本机、同权限进程检查或管理员访问。

未确定主密钥保存保护、解锁方式及保护目标前，不开始实现加密存储，不以“独立随机密钥”或“文件已加密”代替该决策。自动解锁方案如只能保护意外明文暴露或部分离线拷贝场景，须按实际能力说明，不能承诺阻止同权限程序解密。

### 4.2 Codex 运行配置

产品有独立、全局共用的 Codex `config.toml`，管理固定版本实际支持的其他运行选项，例如思考级别、审批、沙箱、工具和 MCP。

客户端的设置控件是该文件的编辑界面：

1. 打开页面读取实际文件，而不是客户端维护的第二份配置副本。
2. 保存时仅更新相应字段，保留未展示的合法配置和必要可读性内容；保留不等于允许其绕过启动边界。
3. 使用固定版本的字段与允许值；格式错误、未知字段和不支持的选项明确处理。
4. 保存采用校验、并发修改检测与原子替换，避免覆盖外部编辑或产生半写文件。
5. 第一版不在执行中热重载运行配置；保存后对下一次启动的编程运行时生效，页面明确提示。
6. 不自动导入个人 Codex 的配置、插件、MCP 或 Hook。产品明确接入的扩展能力再分别验证。

提供商标识、认证来源、模型连接字段属于客户端受控范围；不能通过“其他运行配置”间接重新定义它们。

配置文件仍是运行选项的唯一持久化来源；启动时形成的有效配置只是本次运行的派生结果，不是第二份可编辑配置。首版只放行已按固定版本验证的选项。不支持的扩展不自动启用，未知配置不直接透传；无法保证有效配置符合要求时，拒绝启动该任务并返回字段名或错误类别，不返回敏感值。

## 5. 模型由客户端控制的执行规则

### 5.1 正常调用链

1. 新建会话时确定项目目录，绑定当前连接身份，即代理地址与模型名称；凭据修订号另行记录。
2. 启动前由宿主读取、验证并解密模型连接信息。
3. 启动适配层生成专用 provider 的有效配置，明确指定地址、认证方式和模型，并固定 `wire_api = "responses"`；第一版不允许改为 Chat Completions。
4. 初始化完成后，创建线程时明确指定 provider 与模型。
5. 开始轮次时明确传入会话绑定的模型，并从当前运行配置快照取得思考级别等参数。
6. 恢复会话时核对会话、线程、连接身份和项目目录的对应关系；采用当前有效凭据，不依赖旧密钥。
7. 代理不可达、认证失败、模型不支持或协议不兼容时明确失败，不切换个人登录、普通聊天模型或其他代理。

只允许客户端的受控适配层发送模型相关参数，不开放任意 RPC、启动参数或任意配置覆盖入口给页面。此约束覆盖产品支持的全部编程模型调用，不仅是主线程；独立审查、子代理默认模型及角色配置文件也不能另选模型。

第一版不开放尚未验证的子代理、角色模型覆盖和独立审查入口。后续启用时，必须证明其使用客户端指定的同一连接和模型，并验证运行时显式模型覆盖入口；仅屏蔽配置字段不足以通过验收。

### 5.2 配置文件中的连接与认证字段无效

这不是“两份配置发生冲突后让用户选择”的机制。无论文件中手动写入什么，进程都不得采用文件中的模型连接和认证来源。

实施前按固定 App Server 版本列出完整受限字段及间接入口，至少核查以下类别：

- 模型选择、provider 选择及 provider 定义。
- 审查模型、子代理默认模型、角色配置文件及运行时显式模型覆盖。
- 上游地址、认证头、凭据环境变量引用和外部凭据助手。
- 个人登录、认证存储位置与配置 profile 的间接选择。
- 可能覆盖密钥过滤和受控启动行为的环境、Hook 或其他执行入口。
- 数据库、日志、认证缓存等存储重定向，以及取消必要目录保护的权限配置。

统一启动适配层按以下步骤构造本次运行的有效配置：

1. 解析产品运行配置，检查已支持的字段与允许值，排除模型连接、认证和其他受限来源。
2. 从客户端解密配置构造完整的专用 provider；不得只修改地址和 `env_key`，却保留同名表中原有的 `auth`、OAuth 或额外认证头。
3. 加入产品强制的凭据过滤、目录和权限规则，再确定线程与轮次模型参数。
4. 使用固定版本已验证的加载或覆盖机制启动，核验有效配置与接收方行为；若原生配置合并不能排除受限字段，须使用经验证的受控配置输入，不能把含受限字段的原文件直接作为有效输入。
5. 任何安全必需字段无法强制生效、被系统要求限制或无法验证时，停止任务启动，不修改机器级配置来绕过限制。

不能仅凭字段名猜测，也不能把“启动参数优先”当作所有认证入口已经忽略的证据。固定版本与具体加载方式是实施验证项；上面的统一构造与失败拒绝规则是既定设计，不再由各入口自行选择覆盖、清理或透传。只操作产品自己的文件，不通过定时任务反复重写用户配置文件。

### 5.3 检查时机

| 时机 | 行为 |
| --- | --- |
| 客户端保存配置 | 立即校验受限字段与必要隔离规则 |
| 每次启动 App Server 前 | 重新读取，完成过滤与有效配置校验 |
| 创建、恢复及发送任务 | 校验连接身份、当前凭据修订和受控模型参数 |
| 后台定时检查 | 检测文件中的受限字段、隔离规则及异常修改，记录处理结果 |

定时检查周期待实施时确定；第一版只维护一个全局定时检查，不同时增加文件监听和每会话轮询。它不能替代启动前检查。检查不打印字段值或秘密，不读取个人 Codex 文件；对未变化的同一问题去重，避免日志泛滥。定时检查不反复清理或重写整份配置。

**定时检查不是模型控制的安全窗口。** 受限字段从一开始就不生效。运行中发现文件变化，不切换模型、不重新认证、不自动重启或重发任务；后续启动仍执行完整过滤。

### 5.4 全局模型连接配置变化

第一版区分连接身份与凭据修订，避免换密钥就丢失上下文：

- 存在运行中的编程任务时，不允许替换全局模型连接配置。
- 只更换 API Key，地址和模型不变：更新凭据修订，结束仍持有旧密钥的空闲运行进程；下次执行用新密钥重新启动，并恢复原线程，保留上下文。
- 地址或模型发生变化：新会话采用新连接；旧会话保留历史，继续执行时明确要求新建会话，不静默改路由或复制历史。
- 不保存旧密钥供旧会话使用。凭据更新须原子完成；更新失败保留原配置，成功后才淘汰旧进程。
- 同连接换密钥恢复必须经过真实 App Server 验证。恢复失败明确停止，不创建空线程或自动重发消息，也不要求用户仅因密钥修订号变化就丢弃会话。
- 思考级别等运行选项保存在 Codex 配置文件，不进入客户端加密模型配置。

方案一控制的是产品正常配置和调用链，没有独立的逐请求网关校验层。代理服务端是否重新映射模型，不由客户端请求中的模型名称证明。

### 5.5 Responses 端点与兼容性

- 标准路径为 `/v1/responses`，不是 `/v1/response`，也不是 `/v1/chat/completions`。
- 客户端保存代理基础地址，例如 `https://gateway.example/v1`，App Server 在该地址下请求 `responses`。设置页明确地址填写规则，避免把完整请求路径当作基础地址而重复拼接；无法确认的地址明确提示，不自动猜测路径。
- 使用专用 provider，不要求上游必须是 OpenAI 官方服务器，也不按模型品牌判断协议支持。
- 代理没有 `/v1/models` 或 Codex 模型目录接口时，允许手动填写模型 ID，不以列表接口缺失判定连接失败。成功标准是生产一致的实际推理和工具调用，而不是模型目录能否列出。
- 连接检查至少验证认证、指定模型、HTTP 流式 Responses 事件及工具调用与结果回传。代理有同名路径或普通文本能返回，不代表已满足编程接入。
- 图片与推理级别按实际模型能力验证；不支持图片或所选参数时明确提示，不静默丢弃图片或更换模型。
- 仅支持 Chat Completions、返回对应流式格式，或采用供应商自定义请求格式的端点，第一版明确判为不兼容。不自动尝试另一个协议，不新增本地转换层。

## 6. 密钥的运行隔离

### 6.1 传递与持有范围

App Server 直接请求代理，因此运行期间必须持有真实认证凭据。宿主在启动阶段通过必要的私有链路提供密钥，不通过命令行、全局环境变量、配置文件或消息正文传递。

若采用进程环境注入：

- 使用产品专属变量，只提供给本次受控启动链。
- 构造环境白名单，不全量继承宿主进程中的其他模型、云服务、个人登录及内部令牌。
- 复用 Python 会话客户端时，必要的适配进程也属于受信任凭据边界，不能声称密钥只存在于 Rust 或 App Server。
- 不自行承诺进程退出后内存已被可靠擦除；尽量缩短明文持有时间和不必要的复制。

### 6.2 不向工具传播

- Shell 子进程使用固定版本可用的环境白名单与显式密钥排除规则，禁止通过 `set` 或其他覆盖重新带入。
- 首版关闭个人 Shell profile 自动加载、登录 Shell 和 Shell 快照。按固定版本验证 `allow_login_shell`、`shell_environment_policy.experimental_use_profile`、`features.shell_snapshot` 等对应能力，不把仅过滤初始环境当作启动文件不会重新注入凭据的证据。
- MCP、Hook、凭据助手及其他子进程分别核查。第一版未验证的扩展入口不自动启用。
- 配置编辑不能取消产品强制隔离规则；加载和后台检查均覆盖这些规则。首版不允许用 `danger-full-access` 或其他权限设置解除必要保护；审批授予也不能默认为可解除这些保护，具体边界按固定版本验证。
- 配置目录、模型加密文件及密钥材料不作为普通项目输入或工具工作目录。
- 项目指令和项目配置不得获得覆盖模型连接与密钥隔离策略的权限；具体读取、合并和沙箱行为必须验证。

该机制主要降低密钥被工具继承、打印并进入上下文的风险，不等于操作系统级的进程秘密隔离。应验证工具读取父进程信息、文件或外部凭据入口的实际权限边界，不以“执行 env 看不到密钥”作为全部隔离证明。

关闭登录 Shell 或快照可能影响依赖个人初始化文件的开发工具；先按平台验证必要工具，再通过明确的非敏感环境配置补齐，不为兼容而恢复整份个人环境。工具即使主动调用其他 Shell 或读取凭据助手，也仍须受文件与进程访问边界约束；关闭入口本身不能替代这些约束。

### 6.3 日志与错误

记录操作开始、配置版本、线程建立或恢复、审批状态、停止、结果和清理结果。日志关联使用会话和操作标识。

不输出 API Key、认证头、进程环境、解密密钥、完整模型配置或可能回显凭据的原始上游错误。错误保留有排查价值的阶段、类别和状态码；调试日志、崩溃报告和支持导出也须执行相同规则。

远程模型请求默认使用 HTTPS；本机明文 HTTP 兼容如需支持，单独明确适用范围与验证，不默认向远程 HTTP 地址发送密钥。

## 7. 与个人 Codex 的隔离

### 7.1 程序、目录与认证

产品准备并使用独立、固定版本的运行程序，不要求普通用户自行安装或操作个人 Codex，不执行全局 npm 安装、升级或个人登录命令。

```text
产品自有目录/
  programming/
    model-connection.enc       客户端加密的全局连接信息
    codex-home/
      config.toml              全局运行配置；不保存真实模型连接信息
      ...                      App Server 自有线程与状态
    sessions/
      <会话ID>/                会话元数据、附件与线程对应关系

产品运行资源/
  programming-runtime/         产品管理的固定版本二进制
```

这是逻辑结构，不是已经确定的发行包绝对路径。具体目录遵循当前产品资源与存储约定。所有产品 App Server 显式指定独立的全局 `CODEX_HOME`，线程按会话区分，不复制多份全局配置。

- 不读写个人 `.codex/config.toml`、`auth.json`、历史、缓存或插件。
- 不导入、刷新、退出或删除个人 Codex 认证；不使用个人 Codex 的系统凭据条目。
- 不调用默认落入个人目录的迁移流程。
- 不修改系统或用户全局 PATH、HOME、USERPROFILE 等设置。
- 更新、恢复、卸载只处理经过校验的产品自有目录。

除 `CODEX_HOME` 外，数据库、日志、认证缓存和固定版本提供的其他状态路径都纳入统一启动边界：

- 清理继承的 `CODEX_SQLITE_HOME` 等重定向环境变量，约束 `sqlite_home`、`log_dir` 等配置的实际目标位于产品目录。
- 校验目录及其父路径中的符号链接、Windows junction 等重定向，不只做字符串前缀比较；目录不安全或无法确认归属时拒绝启动或清理。
- 禁用个人认证回退，不启用 `auto/keyring` 认证缓存。优先验证固定版本的 `cli_auth_credentials_store = "ephemeral"`；若不支持，先证明替代方式不读取系统个人凭据、不持久化本次密钥，否则停止接入。
- 不为产品配置修改系统级 Codex 要求；遇到无法满足的机器级限制，明确报错。

独立 `CODEX_HOME` 不自动阻止项目级或系统级配置加载。需按固定版本检查它们对 provider、环境、Hook、工具与权限的影响，不能仅验证目录变量就宣称全部隔离。

### 7.2 进程与文件访问

- 所有产品自有进程经共享进程管理器启动，登记并覆盖后代进程树。
- 正常完成、失败、超时、取消和托盘退出均维护登记与清理状态。
- 退出先阻止新进程，再回收产品进程，最后退出后台。
- 不按 `codex` 等名称批量杀进程，不扫描或接管个人服务。
- Windows 探测与后台运行不弹终端，路径保持普通 Win32 格式；macOS 使用对应进程组和权限适配。

产品生命周期“不主动修改个人配置”与“编程工具不能修改个人配置”是不同验收项。工具读写须采用实际可验证的目录与审批策略，不能默认拥有个人 Codex 目录的写权限，也不能把独立数据目录当作工具访问控制已经完成。

复用会话客户端时须检查真实启动参数和 App Server 有效权限，不能以包装层中的权限变量、日志名称或回调存在就认定沙箱已生效。

## 8. 界面、会话与识图

- 设置左侧在“模型”与“Profile 管理”之间增加“编程”，标明配置为全局共用，不显示 Profile 配置选择器。
- 分别提供模型连接设置与 Codex 运行设置；后者的控件直接对应配置文件。
- 普通聊天和编程会话通过左侧各自的入口打开，不在启动空态或输入框中提供“普通 / 编程”切换。编程会话显示全局编程模型，未配置时提供设置入口。
- 第一条消息发送后固定会话模式；旧普通聊天保持原有行为。
- 编程历史全局可见，在现有左侧 Profile 会话列表下方增加“编程会话”区域，按实际项目目录分组，文件夹行下展示会话；项目以稳定 ID 持久保存名称与地址，支持详情弹层、编辑名称和地址、逐项目展开/收起、展开更多与在该目录新建会话。改地址只影响新会话；旧会话保留原目录与上下文，并继续归属原项目。完整路径区分同名项目。模型连接仍为客户端全局一份，与目录分组无关。在原页面右侧聊天区域打开，不使用单独页面或区内历史下拉框。切换 Profile 不改变编程会话归属；点击普通会话时显示普通聊天，点击编程会话时恢复对应的编程上下文。
- 编程发送前明确选择项目目录；恢复会话沿用原目录，目录不可用时明确提示。
- 每个会话对应独立线程、历史与执行状态，不因共用模型、密钥或 `CODEX_HOME` 而共用上下文。
- 图片选择、拖入和粘贴复用现有附件交互，按会话管理。图片按 App Server 支持的输入传递，不仅发送路径文字；代理与模型必须实际支持视觉。
- 停止、失败、恢复与断线不自动重发任务；失败的线程恢复不悄悄创建空线程继续执行。

## 9. 验证与验收门槛

| 类别 | 必需验证 |
| --- | --- |
| 客户端加密 | AES-256-GCM 与成熟实现、完整性校验、错误解锁、保存失败与原子更新；各安装实例密钥不同、nonce 不复用、升级保留密钥、密钥丢失不覆盖；不调用系统凭据存储、不明文回退 |
| 配置唯一来源 | 模型连接仅来自客户端；同名 provider 中残留认证表或头不能生效，无法保证时拒绝启动 |
| 全部模型调用 | 主线程使用指定模型；未验证的审查、子代理及角色覆盖入口被关闭，后续支持时验证实际模型请求 |
| 间接覆盖 | provider 定义、环境引用、认证助手、项目配置、启动快照等不能绕过受控连接与必要隔离 |
| 定时检查 | 发现修改、去重记录、失败恢复，不切模型、不重启任务、不误读个人目录 |
| 接收方协议 | 生产一致的 Responses 请求、SSE 事件与工具调用往返被固定 App Server 和代理接受；缺少模型列表仍可指定模型执行；错误密钥、模型及 Chat Completions-only 端点明确失败，无协议回退 |
| 工具凭据 | 工具子进程不继承测试密钥标记，输出、日志、配置和会话记录不含密钥；Shell profile、登录 Shell、快照、文件及父进程读取入口分别验证；必要启动适配进程的明文持有单独记录 |
| 密钥更新 | 地址和模型不变时换密钥、淘汰旧进程并恢复原线程；失败不重发任务、不丢弃上下文、不使用旧密钥 |
| 上下文与图片 | 多轮、工具调用、图片、历史恢复和会话切换不串用 |
| 生命周期 | 正常、失败、超时、停止和退出均回收指定进程树，拒绝退出期新启动 |
| 个人 Codex | 个人配置和认证前后不被产品更改；数据库/日志重定向、目录链接和认证缓存不能落入个人空间；个人进程并行运行不受产品启停影响 |
| 配置编辑 | 保留未知合法字段、处理外部并发修改、格式错误与保存失败，不覆盖无关内容 |

密钥测试使用构造的标记值，不把真实密钥打印进测试输出。模型与协议验证须覆盖真实接收方，不仅断言本端生成了预期字符串。

Windows 与 macOS 分别记录命令、环境、结果及未验收范围。类型检查、构建、模拟测试、真实协议、原生窗口和安装包验收是不同层次，不相互替代。

## 10. 实施顺序与待定项

实施顺序：

1. 确定每安装实例 AES-256-GCM 主密钥的保存保护与解锁方式，固定 App Server 二进制及 Responses 配置协议。
2. 在统一启动适配层验证完整 provider、受限字段忽略、全部模型入口、存储路径和工具凭据隔离，再验证真实代理文本/图片及同连接换密钥恢复。
3. 在产品适配层接入会话生命周期、恢复、审批、取消和日志，不修改锁定 fork。
4. 接入全局设置、配置文件图形化编辑、新聊天模式和独立会话展示。
5. 完成双平台隔离与回归验证，再按仓库规则记录实际开发状态。

尚需明确或验证：

- 已确定 AES-256-GCM、每实例独立随机密钥及产品私有目录自动解锁；密钥丢失或损坏必须报错，不覆盖已有加密配置。
- 已固定 GitHub tag、平台资源及 SHA-256，默认不随包分发；后续版本变更更新锁文件并重新验收，不自动跟随 latest。
- 固定版本受限字段清单与统一有效配置构造的具体加载方式，不能以原文件直接透传或轮询修补代替。
- 一个全局定时检查的周期，以及配置编辑器对外部并发修改和注释的处理能力。
- 支持的首批运行选项、扩展入口、Responses 兼容代理与视觉模型的实际验证范围；不重新引入 Chat Completions 支持。
- 双平台沙箱对个人配置、父进程信息及其他凭据入口的实际限制。
