# 本地网页应用平台方案

状态：方案，尚未实施。编写日期：2026-11-05。依据为当前 `feature/v0.1.9` 工作树和锁定 Hermes fork 的实现。本文描述拟实现的功能，不代表已经交付或通过原生验收。

## 产品定位

让用户开发网页应用，安装到 Hermess Agent Desktop，并在本机桌面客户端内打开。**应用是独立的一等对象，不要求创建或绑定 Agent。** Personal Agent 是可选能力：应用需要聊天、模型、任务等 AI 功能时，才由用户选择一个现有 Profile 连接。

本地运行阶段同时支持两类应用：纯前端静态网页，以及前端加本地服务端的完整 Web 应用。服务端可以使用 Node、Python、Rust 或其他技术栈；平台不把某种语言作为应用定义，但必须能在目标操作系统上启动并满足约定的健康检查。用户已有的远程服务也可以作为页面或 API 来源，但客户端只连接它，不负责在远端部署。云端托管与应用发布另行规划。

## 首版用户流程

1. 从模板创建纯前端或前后端应用，按所选技术栈构建可在本机运行的产物。
2. 在客户端的独立“本地应用”入口选择应用目录。客户端展示应用名称、版本、页面入口、服务端启动要求和声明的能力，校验后安装到产品自有数据目录。
3. 从应用列表打开页面。静态应用直接加载；前后端应用先启动自有服务端，健康检查通过后再打开页面。服务端启动失败、超时或异常退出时显示具体状态和重试入口。
4. 普通应用无需连接 Hermes Gateway；需要 AI 能力的应用在明确连接目标 Profile 后使用受约束的宿主接口。
5. 作者修改代码后重新构建，使用“重新导入”更新；更新失败保留可运行的旧版本。用户可停用、重新启用或卸载应用，客户端清理页面、服务进程及产品管理的资源。

首版不提供应用市场、分享发布、账户同步、远程托管、公开网址或多用户访问。

## 当前代码事实与需要新增的能力

| 当前事实 | 对方案的影响 |
| --- | --- |
| `apps/frontend/src/features/dashboard-plugins/DashboardPluginHost.tsx` 已能按 Profile 读取 manifest、加载插件资源和注册页面。 | 可以参考其导航和生命周期处理，但它以 Gateway 插件和 Profile 为中心，不应直接把所有网页应用伪装成 Hermes 插件。 |
| `apps/frontend/src/features/profiles/ProfileHermesPlugins.tsx` 的安装入口接受 Git 标识或 HTTPS 地址。 | 这是 Agent 插件管理，不是普通本地网页应用的安装入口；不能把本地目录直接传给现有 Git 安装接口。 |
| 锁定 fork 的 `hermes_cli/web_server_dashboard.py` 从插件根目录发现 `dashboard/manifest.json`。 | 该发现路径依赖 Gateway，且用户插件目录主要以 Gateway 启动根目录为单位；普通网页应用应由产品客户端独立登记和加载。 |
| 桌面客户端已有自有数据根、Tauri 宿主适配层和共享进程管理器。 | 本地应用资源、元数据和由产品启动的服务端进程均须留在产品管理范围内，与用户另装的 Hermes 隔离。 |

因此，首版新增**产品级本地应用管理与页面容器**，而不是扩展现有 Profile 插件页来承载一切应用。已有 Dashboard 插件继续走原流程；需要 Agent 深度扩展的应用可在后续定义插件适配方式。

## 应用包与安装

模板分别给出纯前端和前后端示例。应用清单至少声明稳定 ID、名称、版本和运行模式。静态模式声明入口 HTML；本地服务模式声明平台对应的启动入口、参数、工作目录、就绪检查和页面路径；连接已有远程服务的模式声明 HTTPS 来源。可选声明图标、描述及是否请求 AI 宿主能力。具体字段和版本号在实施前以 Schema 固定，不把开发机绝对路径、凭据或固定端口写入包中。

客户端导入时校验清单、入口文件或服务端可执行入口、资源路径、文件数量与总大小；拒绝路径穿越、越界符号链接、重复 ID 的意外覆盖和损坏文件。服务端依赖需明确：可随应用包携带，或由应用声明本机前置条件并在启动前探测；平台不默默执行安装脚本。校验通过后先复制到产品自有暂存目录，再切换为当前版本。源项目仍由作者管理；本地运行时不直接引用源目录，也不要求 Git 仓库或网络连接。Windows 路径在存储及前端状态中使用普通 Win32 写法；macOS 使用原有路径规则。

更新沿用同一应用 ID，先完成新版本校验和暂存。运行中的服务端先按受管流程停止，新版本就绪后再切换；若新服务无法启动或通过健康检查，恢复旧版本及其可运行状态，不能只回滚文件而留下新进程。卸载只清理此产品创建的应用资源、进程及登记记录，不删除作者源代码。应用持久数据使用独立目录，升级时保留；卸载时提供明确的保留或删除选择，不能混入构建资源目录。

## 桌面运行与可选 Agent 接入

普通应用的页面与本地服务生命周期应独立于 Gateway：Gateway 未启动、模型未配置或 Profile 切换时，普通网页应用仍可打开。应用列表和导航展示产品级安装记录，而不是从 Gateway 插件列表反推。

建议为本地网页应用提供独立页面容器。静态资源从产品可控的本地来源加载；本地服务仅监听回环地址，由客户端分配端口并确认端点属于当前应用，再打开其页面；已有远程服务仅允许用户明确配置的 HTTPS 来源。实施前需在 Windows WebView2 与 macOS WebKit 上验证资源加载、路由刷新、登录 Cookie、跨域请求、窗口关闭和来源隔离；远程站点如禁止嵌入，应明确提示并用系统浏览器打开，不伪称已嵌入。应用默认不获得 Tauri 命令、文件系统或 Gateway 凭据；确需宿主能力时，通过小而明确的桥接接口逐项开放。不能仅靠隐藏前端按钮作为权限控制。

AI 能力采用显式连接：应用声明需要的能力，用户选择目标 Profile，桌面宿主核对该 Profile 正由产品 Gateway 服务，再把已允许的操作路由到该 Profile。切换 Profile、断线、停用或卸载应用后，旧连接失效。首版示例只选一个经当前接收端验证的最小能力；不一次性暴露现有 Dashboard 插件 SDK 的全部接口。涉及新 Gateway 请求时，必须追踪生产调用和锁定接收端，并验证真实接受与拒绝结果。

本地 HTML/JS 和服务端可执行代码属于用户导入的代码。首版定位为运行自己信任的应用；在独立来源、宿主命令限制及跨平台行为得到验证前，不宣称能安全运行任意第三方应用。

## 本地服务端运行

前后端应用的服务端由桌面客户端启动，而非由网页 JS 自行拉起。启动参数、工作目录、环境变量与数据目录由产品适配层按应用清单构造；密钥不得放入清单或日志。服务只绑定 `127.0.0.1`（macOS 可按同一回环原则处理），端口由客户端协调，避免硬编码与其他应用冲突。必须验证服务确由本产品启动，不能因某端口已响应就接管用户已有进程。

每个服务端及其后代都要进入现有共享进程管理器。启动、就绪、异常退出、超时、用户关闭、更新、卸载与托盘退出均维护登记和回收状态；Windows 后台启动不得闪现终端窗口。服务端可持续运行到用户停止应用或退出客户端，但运行策略要明确，不能关掉页面后留下未知进程。页面只能连接已确认归属的端点，健康检查和 API 路由要分别验证。已有远程服务由用户或其服务提供方管理，客户端只管理连接，不接管远程进程或数据。

## 实施顺序

1. **固定应用契约**：确定静态、本地服务及已有远程服务的清单 Schema、模板、资源加载方式和最小宿主能力；分别用一个页面和一个小型 HTTP 服务验证 Windows 与 macOS 的容器行为。
2. **实现产品级管理**：增加本地应用列表、导入、校验、暂存、启停、更新与卸载，按现有桌面契约和存储所有者接入。
3. **接入页面与服务生命周期**：处理导航、页面加载、服务端启动/健康检查、失败/重试、重启恢复、端口归属、页面关闭、更新回滚和托盘退出；验证无 Gateway 时普通应用可用。
4. **加入可选 AI 桥接**：只开放示例所需的已验证能力，明确目标 Profile、状态和错误处理；回归 Profile 切换及 Dashboard 插件。
5. **双平台验收**：分别记录 Windows、macOS 的原生客户端和安装包结果，并更新 `ROADMAP.md` 的开发范围、实际验证及未完成项。

当前 `ROADMAP.md` 曾将桌面插件 SDK 排除在 `v0.1.9` 原定范围之外。开始实施本方案时，应先按仓库版本流程确定对应版本并同步路线图；计划、构建通过和原生验收分别记录。

## 首版验收标准

- 构建一个不使用 Agent 的静态网页应用，离线导入后能在桌面内打开；Gateway 停止时仍能使用。重启客户端后应用列表和页面可恢复。
- 构建一个前端加本地 HTTP 服务的应用，验证服务启动、实际 HTTP 响应、页面调用、失败重试、异常退出、更新回滚和托盘退出时的进程树回收；不得把前端模拟响应计作服务端验收。
- 对已有远程 HTTPS 服务，验证已授权来源能打开或明确提示只能在系统浏览器打开；连接失败、证书错误和断网均有可理解的状态。客户端不宣称已部署该服务。
- 非法清单、入口缺失、资源越界、重复 ID 和损坏构建均给出明确错误，且不破坏已有版本。
- 重新导入成功后显示新版本；失败时旧版本仍可打开。停用、启用、卸载后的导航、资源和登记状态一致。
- 用第二个示例应用验证可选 AI 连接：目标 Profile 明确，切换或断线后旧请求不能继续使用；拒绝路径由宿主和锁定接收端实际验证。
- 导入、更新、打开失败和清理的日志能串起操作与结果，不记录凭据、令牌或页面内容。
- 原有 Git 插件安装、Dashboard 插件页面、Profile 切换、受管进程回收和客户端退出行为没有回归。
- Windows 与 macOS 分别记录原生验证；浏览器预览、单测、构建与安装包操作不相互替代。

## 远期部署

本地前端和本地服务稳定后，再设计应用包分发、签名与审核，以及由平台负责的云端部署。连接用户已有服务不等于平台部署了该服务。云端阶段另需账号、租户隔离、远程运行时、持久化、访问控制和运维。
