# 前端与桌面客户端架构演进方案

状态：分阶段实施中。适用基线：`HermessAgentDesktop` 的 `feature/v0.5.0`。本文定义目标代码边界和迁移验收；目录树是完成形态，不能据此认定每个模块已落地。实际进度以 [路线图](../ROADMAP.md) 和 [能力矩阵](capability-matrix.md) 为准。

## 1. 目标与决策

将产品整理为同一仓库中的三个工作区项目：**前端**、**桌面客户端**和**接口契约**。前端负责界面及用户交互；桌面客户端负责 Tauri 宿主、原生能力和 Hermes 运行时；契约项目定义两者共享的调用、事件和数据格式。三个项目都必须有自己的 `README.md`、`AGENTS.md` 和按要求提供的 `agent.md`。根目录文档负责整体开发与发布流程。

目标不是增加目录数量，而是让新功能能沿一条明确路径落地：前端 View 与组件 → 前端能力接口 → 桌面适配层 → Rust 功能模块 → Hermes 或操作系统。每一层有独立的职责、可替换的实现和可验证的边界。现阶段仍交付一个桌面产品、一个安装包版本；三个工作区项目不意味着三个独立发布物。

采用单仓库和 pnpm workspace。这样前端、接口和原生实现可以在同一变更中演进，CI 能检查跨层契约，Tauri 打包仍使用本仓库固定的 Hermes 运行时与发布流程。未来新增其他宿主时，复用前端与契约，再实现新的宿主适配层；不要求现在建设 Web 服务或把本地运行时暴露到网络。

### 必须保持的产品边界

1. 只有桌面客户端创建、持有、重连和停止本产品的 Hermes 子进程；存储锁、子进程句柄、端口、随机凭据和 Gateway 连接属于同一个运行时所有者。不得通过端口扫描接管用户已有的 Hermes 实例。
2. 上游 Hermes 继续由 `runtime/upstream.lock.json` 锁定来源、tag 和完整提交；产品源码不直接修改 `vendor/hermes-agent`，也不恢复 submodule。
3. 前端不能访问原生文件系统、进程或凭据存储；这些操作经桌面能力接口进入宿主。现有聊天、附件、模型配置等交互中的必要输入可以由前端提交，但持久化和对上游的鉴权留在桌面客户端。
4. 分层迁移不得把脚本冒烟、前端构建或 CI 构建写成原生窗口及真实模型验收。

## 3. 前端内部架构

### View、组件与状态

`App` 只负责产品布局、页面导航和少量跨页面状态。现有五个页面分别成为 `ChatView`、`ModelSettingsView`、`AgentSettingsView`、`RuntimeView` 和 `ToolsView`。View 组合本功能组件，处理加载、空态和错误展示，并通过注入的能力接口触发用例；View 不直接导入 Tauri。

功能组件放在所属功能目录，例如聊天的消息列表、输入框、附件队列、审批卡片和模型选择器，Agent 设置的配置树、字段编辑器与 YAML 编辑器。只有两个以上功能确实共用且语义一致的组件，才进入 `shared`。共享的是行为和表达，不以视觉相似为唯一依据。

会话状态、事件补发、审批请求、附件暂存等状态逻辑与所属功能放在一起。特别是聊天重连涉及 `replay_epoch`、事件序号、快照和缓冲事件，必须由同一聊天控制器协调；拆分 JSX 时不能把这些状态留在新的巨型 `App` 中。纯解析、过滤和格式化函数用普通模块；只有依赖 React 生命周期的逻辑才写成 hook。

前端状态分为三个范围：组件局部状态、功能状态和跨页面共享状态。优先使用 React 自身能力，确有跨功能同步需求时才引入全局状态库。页面的瞬时输入不进入全局状态；来自 Hermes 的会话事实以客户端返回值和事件为准。

### 生产装配与预览

前端导出 `mountApp(root, desktopApi)`，内部只依赖契约项目。桌面项目的 `src/main.tsx` 注入 Tauri 实现并调用它；Tauri 仍从 `apps/desktop/dist` 加载单一生产产物。前端项目的浏览器预览入口注入模拟实现，用于页面开发和交互检查。模拟实现不得冒充真实后端、原生窗口或安装包验证。

这一装配方式允许前端独立进行类型检查和预览，也让桌面安装包继续沿现有 Tauri 构建路径交付。正式构建只有一个生产入口，避免维护两套页面。

## 4. 桌面客户端内部架构

### Rust 模块的所有权

`runtime` 是自有 Hermes 实例的唯一生命周期所有者。它持有存储锁、子进程、随机凭据、端口和 Gateway 连接，负责启动、探活、重连、停止及失败后的资源释放。当前 `runtime/location.rs` 负责存储定位与所有者锁，`runtime/payload.rs` 负责固定资源校验和解包；它们不各自持有一份可变运行时事实。功能子模块使用显式导入，避免依赖父模块的全部导入。

`gateway` 封装当前固定上游的 WebSocket/RPC 协议：请求关联、超时、鉴权、事件转发、审批与澄清请求。上游协议变化在这里适配；聊天和模型模块调用有语义的方法，不重复拼接底层帧。事件序号与进程纪元仍按当前固定上游的实际协议处理。

`runtime/chat.rs` 处理会话创建、消息、命令、附件和恢复；`runtime/models.rs` 处理模型查询、切换、默认模型和自定义端点；`runtime/config.rs` 处理配置读取、字段保存和完整 YAML；`runtime/tools.rs` 处理 Agent 工具目录和随包工具清单；`diagnostics.rs` 处理本机探测与产品日志。它们使用同一个运行时所有者，不各自持有进程或凭据。一个功能若只含简单 Gateway 转发，可以直接在所属模块提供 Tauri 命令，不强制经过额外的 `commands → services → adapters` 三层。

`main.rs` 只做 Tauri 初始化、插件、状态注入和命令注册。Rust 公共模块暴露最小接口；校验放在信任边界，跨模块用有意义的数据类型，避免大量 `serde_json::Value` 穿透全部层级。协议边缘仍可使用 JSON 值，以兼容当前上游动态响应。

### 桌面 TypeScript 适配层

桌面项目的 TypeScript 只负责将 `DesktopApi` 映射到 Tauri `invoke`、事件订阅、原生文件选择和 Webview 拖放。它不包含页面 JSX、提供商展示规则、聊天状态机或国际化文案。订阅接口必须返回取消订阅函数；窗口销毁、页面卸载和重连时按同一规则释放监听。

## 5. 接口契约与扩展方式

`packages/contracts` 按能力分组定义接口：`runtime`、`chat`、`models`、`agentSettings`、`tools`、`nativeFiles`、`diagnostics` 和 `events`。前端依赖这些接口；桌面适配层实现它们。接口只承诺产品需要的能力，不镜像全部 Tauri 命令或 Hermes RPC 方法。

跨语言 DTO 与事件载荷逐步进入 `schema/`，由其定义字段、可选性、版本和错误类别。已迁入的启动结果、实时事件、审批/澄清请求及补发结果由 Schema 生成 TypeScript 类型；Rust 的启动结果、实时事件和请求用共用样本验证序列化，补发结果仍是 Gateway 原样透传。其余 DTO 和稳定错误类别尚未完成迁移。生成结果必须可复现且由 CI 检测漂移；不以两边各自手写一份类型作为长期方案。

事件至少区分数据事件、需要回应的请求和连接状态；定义会话标识、序号、纪元、取消与去重语义。命令失败使用稳定的错误类别和可本地化的错误码；原始上游错误、令牌和配置正文不直接成为用户界面错误。现有命令名、事件名及 payload 在迁移期保持兼容，直到新契约及回归检查同时生效。

新增宿主时实现契约接口。新增前端功能时先确定所属 feature，再扩展最小能力接口和桌面实现。新增原生工具能力时由相应模块承接，不能把业务逻辑放进通用 `util`。`util` 只接纳无状态、无业务所有权、被多处使用的纯函数。

## 6. 依赖规则

```text
frontend feature ──→ contracts
desktop TS adapter ──→ contracts + Tauri API
desktop production entry ──→ frontend public entry + desktop TS adapter
desktop Rust feature ──→ runtime owner / gateway / 本功能内部模块
gateway ──→ 固定上游协议
runtime ──→ 操作系统、payload 与自有进程
```

禁止前端功能目录导入 `@tauri-apps/*`、`apps/desktop` 或 Rust 实现细节；桌面适配层不能反向导入前端内部 feature 文件，只能使用前端公开入口和契约。契约项目不能依赖前端、Tauri 或上游 Hermes 源码。Rust 模块之间不通过 `main.rs` 互相调用。

这些规则由依赖检查和 CI 执行，而非只写进文档。当前 `pnpm check:architecture` 除检查 TypeScript 依赖方向，还核对桌面适配层调用的每个具名命令均在 Rust 注册、原生事件与订阅名称互相对应，并禁止 Rust 功能模块通过 `use super::*` 隐式依赖运行时所有者的全部导入。对跨层调用建立明确的公开入口，避免相对路径绕过边界。

## 7. 文档与代理规则

每个工作区项目的 `README.md` 必须回答：负责什么、目录如何组织、怎样启动或构建、依赖哪个契约、怎样验证、哪些能力属于别的项目。命令只写仓库真实存在且已核对的脚本；迁移完成后再写新命令。根 README 提供总体架构和三个项目入口。

每个项目的 `AGENTS.md` 是该目录的规则正文，明确可修改范围、依赖方向、代码格式、验证命令、不能越过的运行时和发布边界。按指定文件名提供的 `agent.md` 只链接同目录 `AGENTS.md`，不复制规则。根 `AGENTS.md` 保留全仓库分支、上游锁定、发布和证据要求；子项目只补充自身规则，不能放宽根规则。

## 8. 迁移路线与交付门槛

每个阶段单独提交可审查的变更；在 `feature/v0.5.0` 开发时遵守现有 PR 和路线图规则。阶段完成必须保持可构建，不将纯目录移动与行为改写混在同一提交。

| 阶段 | 交付物 | 通过条件 |
| --- | --- | --- |
| 0. 基线 | 命令、事件、DTO、路径引用和关键交互清单；现有检查结果 | 明确当前命令名、入参、返回值及发布脚本引用；记录未验收场景 |
| 1. 契约 | `contracts` 项目、能力接口、代表性样本 | 前端预览与桌面适配针对同一接口编译；样本在 TS/Rust 两侧兼容 |
| 2. Rust 内聚 | `runtime` 唯一所有者及按功能划分的模块 | 命令名和行为不变；格式、编译、Rust 测试及相关 Gateway 冒烟通过 |
| 3. 宿主适配 | 桌面 TypeScript adapter 与唯一生产入口 | 前端源码不直接调用 Tauri；桌面构建仍产生正确 Webview 资源 |
| 4. 前端拆分 | 五个 View、专属组件与状态逻辑 | `App` 不再承载各页面用例；聊天恢复、审批、附件和配置交互回归通过 |
| 5. 工作区落位 | 三个项目的目录、文档、workspace 与依赖规则 | 本地和 CI 完整构建；发布路径、版本检查、payload 与安装包资源核对通过 |

阶段顺序可按依赖调整，但不能跳过阶段 0 的基线，也不能仅凭 `pnpm build` 宣称阶段 5 完成。现有 `apps/desktop` 路径已被 Tauri 配置、CI、版本检查、离线构建和资源收集使用；优先保留该路径及其 `dist` 位置，降低迁移时对发布链路的冲击。

### 必须回归的用户流程

1. 首次启动、固定 payload 校验与安装、产品存储目录锁、自有进程退出及重新启动。
2. 聊天流、停止、会话历史、重连后的事件补发、纪元变化和截断时的快照恢复。
3. 审批与澄清的接收、回答、取消和断线恢复；普通文件与图片附件的选择、拖入、移除和发送。
4. 模型配置、会话模型切换、Agent 字段与 YAML 保存、工具目录和诊断日志。
5. Windows 本地构建及安装包资源核验；macOS、Linux 的 CI 构建和原生实机结果分别记录，不能互相替代。

## 9. 完成定义

- 新功能能按所属 feature 和客户端模块落位，不需要扩大根 `App`、`main.rs` 或单个后端大文件。
- 前端可以在模拟宿主下独立预览；生产安装包通过桌面适配层装配同一套前端代码。
- 一个运行时所有者控制产品创建的进程、存储锁、凭据和 Gateway；用户已有 Hermes 数据和进程保持隔离。
- 契约类型、事件语义、错误类别及文档与实现一致；CI 能阻止跨层非法依赖和契约漂移。
- 三个工作区项目都具备准确的 `README.md`、`AGENTS.md` 和 `agent.md`；根 README 提供整体入口。
- 现有发布门槛、固定上游校验和按平台区分的验收证据继续有效。只有相应检查真正完成，才把迁移阶段标为完成。
