# 本地网页应用平台：难度评估与落地方案

状态：实施方案，尚未开发。编写日期：2026-11-05。产品范围以 [本地网页应用平台方案](local-web-app-platform-plan.md) 为准：应用可以是纯前端、前端加本地服务端，或连接用户已有的远程服务；Agent/Profile 是可选能力。平台自身的云端部署留到后续。

## 结论与工作量

**难度：中高。** 做一个能打开固定网页的入口并不难；把它做成用户可导入、更新、稳定运行的应用平台，难在页面权限边界、任意技术栈的服务启动、进程树回收、跨平台资源路径和失败回滚。现有仓库已有 Tauri 桌面宿主、产品自有存储和共享进程管理器，能复用基础设施；没有通用网页应用容器和应用包协议。

粗略估算：一名熟悉本仓库的全职开发者，完成“纯前端 + 本地 HTTP 服务 + 已有远程 HTTPS 服务 + 可选的一个 AI 接口”的首版，连同 Windows/macOS 原生验证，约 **6–10 周**。这是方案阶段的工程估算，不是当前进度或交付承诺。若首轮只做纯前端和本地 HTTP 服务的最小闭环，可先按 **4–6 周**规划。时间取决于独立 WebView 容器在两端的实测结果、服务端打包方式，以及现有应用切换和退出链路的回归情况。

| 工作块 | 难度 | 主要原因 |
| --- | --- | --- |
| 应用清单、导入与版本切换 | 中 | 路径校验、暂存替换和旧版本回滚需要完整失败处理。 |
| 桌面内网页容器 | 中高 | 需要让页面可用，又不能让应用网页继承主窗口的原生命令权限。 |
| 本地服务端运行 | 高 | 进程树、端口归属、就绪/崩溃/超时、Windows 无控制台窗口、托盘退出和 macOS 行为均须闭环。 |
| 已有远程服务接入 | 中 | HTTPS、登录状态、跨域和站点禁止嵌入等行为取决于目标服务。 |
| 可选 AI/Profile 接口 | 中高 | 必须明确应用身份和 Profile 归属，不能把完整 Dashboard SDK 直接开放给普通网页。 |

## 当前代码依据

- `apps/desktop/src-tauri/tauri.conf.json` 使用 Tauri 2，当前主窗口 CSP 只围绕产品资源和本地回环资源配置，不能直接当作任意应用的来源策略。
- `apps/desktop/src-tauri/capabilities/default.json` 给主 WebView 配有原生权限和创建子 WebView 的权限；`chat-windows.json` 展示了为特定窗口标签单独配置权限的既有模式。应用页面不能沿用主窗口权限。
- `apps/desktop/src-tauri/src/chat_windows.rs` 已有独立 WebViewWindow 的创建及销毁登记，但这是聊天窗口，不等于已经验证主窗口内的通用应用容器。
- `apps/desktop/src-tauri/src/process_manager.rs` 已实现拒绝退出后新进程、登记进程树和按类型回收；本地应用服务应复用它，而不是另建启动器。
- `apps/frontend/src/features/dashboard-plugins/DashboardPluginHost.tsx` 是按 Profile 加载的 Hermes Dashboard 插件宿主。普通网页应用可以借鉴其导航与状态管理，不能直接使用其脚本注册方式或假定它天然隔离第三方网页。

上述依据来自当前工作树；嵌入式子 WebView 的来源隔离、CSP、Cookie 和跨平台行为仍需原生技术验证。

## 推荐的最小架构

```text
产品主窗口：应用列表、安装管理、状态展示
           │
           ├─ 本地应用管理器（Rust）：校验、版本、数据目录、生命周期
           │       ├─ 静态资源来源：产品管理的应用文件
           │       └─ 服务进程：共享 process_manager → 127.0.0.1 动态端口
           │
           └─ 独立应用 WebView：只加载已登记应用的来源
                   └─ 可选宿主桥接 → 校验应用身份 → 校验目标 Profile → 已核实的 Gateway 能力
```

### 1. 用协议支持不同技术栈

平台只规定**运行协议**，不规定前端框架或后端语言。应用清单区分三种模式：

| 模式 | 应用提供 | 平台负责 |
| --- | --- | --- |
| 静态页面 | 构建后的 HTML/JS/CSS、入口页面 | 校验资源并在独立页面容器加载。 |
| 本地服务 | 可在目标系统启动的服务程序或启动入口、健康检查路径、页面路径 | 启动受管进程、分配端口、确认就绪、打开页面、停止和回收。 |
| 已有远程服务 | 用户明确填写的 HTTPS 来源 | 打开并检查可用性；不部署、不接管该服务。 |

首版服务端契约统一为 HTTP：服务绑定客户端指定的回环地址和端口，提供有界时限的健康检查，再提供页面或 API。Node/Python/Rust 均可实现这一契约。开发阶段允许应用声明本机已有的运行时，但安装检查须明确指出缺失依赖；跨机器分发时再要求作者打包对应平台的运行时或可执行文件。平台不承诺自动安装任意语言依赖，也不默默执行项目安装脚本。

### 2. 应用页面与主窗口分开

优先验证主窗口应用区域内的独立子 WebView：应用网页使用独立来源、独立权限集，不能直接调用主窗口 Tauri 命令。主窗口只负责显示外框、标题、状态和导航。这个容器必须先在 Windows WebView2 和 macOS WebKit 原生客户端证明可加载静态、本地 HTTP 和允许嵌入的远程页面，并正确处理焦点、返回、刷新、窗口尺寸和销毁。

如果原生技术验证发现主窗口内的独立容器无法可靠实现，应先调整页面承载方式和产品交互，再进入安装功能开发；不能退化为把用户脚本注入主窗口。远程网站可能通过自身策略禁止嵌入，客户端应提示并在系统浏览器打开。对这类站点不承诺桌面内嵌。

### 3. 由产品管理本地服务端

Rust 应用管理器是服务生命周期的唯一所有者。每次启动生成操作 ID，验证应用版本与启动入口，分配端口，使用共享 `process_manager` 启动并登记进程树，等待实际健康检查成功后才把页面标记为可用。失败、超时、崩溃、更新、卸载和托盘退出均记录结果并回收；不能只根据某端口已有响应就认领一个外部进程。Windows 后台启动不得弹出控制台窗口。macOS 使用同一业务状态机，平台差异留在适配层。

首版约定“停止应用”即停止其本地服务；关闭页面后是否继续运行由明确的应用运行策略决定，默认不留下未知进程。应用持久数据独立于程序版本目录，升级保留；卸载时明确提供保留或删除数据的选择。

### 4. AI 是可选的窄接口

普通网页应用不需要 Gateway，也不受 Profile 切换影响。若应用声明 AI 能力，用户先选择 Profile，宿主再核对该 Profile 正由产品 Gateway 服务，并只开放该应用声明且产品已实现的接口。每次调用校验应用身份、当前来源和目标 Profile；断线、切换、停用或卸载后旧连接失效。首版先用一个真实接收端验证过的接口做样例，不一次性开放 Dashboard SDK 的全部能力。

## 开发与交付顺序

1. **技术验证**：用隔离测试页面在 Windows/macOS 原生客户端验证独立 WebView、三类来源、权限/CSP、焦点和销毁。另用受管假 HTTP 服务验证启动、端口归属和进程树回收。此步失败时先修订容器设计。
2. **静态应用闭环**：应用清单 Schema、目录导入、校验、暂存、页面打开、启停、重新导入和卸载。先做到离线、无 Gateway 也能运行。
3. **本地服务闭环**：增加启动协议、依赖提示、健康检查、失败重试、异常退出、日志、更新回滚、托盘退出和安装包内运行。示例后端实际处理一个 HTTP 请求。
4. **远程来源与可选 AI**：接入用户已有 HTTPS 服务，明确不可嵌入时的行为；为一个样例应用增加经锁定 Gateway 接收端核实的 AI 能力。
5. **双平台回归**：验证原有聊天窗口、Dashboard 插件、Profile 切换、现有产品进程、存储位置切换和退出顺序。按实际结果更新 `ROADMAP.md`，未完成的原生操作继续标为未验收。

每阶段结束都应留下可运行的样例和真实状态回读。不要把“页面显示了”“脚本返回零”分别当成服务进程或 Gateway 接收端已验证。

## 必须通过的验收场景

- **纯前端**：从本地目录导入、离线打开、刷新、重新导入、重启恢复和卸载；Gateway 停止时仍可用。
- **本地前后端**：服务启动后真实健康检查和 API 请求成功；端口冲突、依赖缺失、启动超时、崩溃、更新失败及退出时页面状态正确，进程树无遗留。
- **远程服务**：HTTPS 来源校验、断网、证书错误、登录状态和站点禁止嵌入的结果准确呈现；不声称平台完成了远端部署。
- **权限与隔离**：普通应用不能直接调用主窗口原生命令、读取其他应用数据或取得 Gateway 凭据；可选 AI 接口只能落到已选 Profile，旧连接失效后拒绝调用。
- **平台差异**：Windows 与 macOS 分别做原生客户端和安装包验收，记录命令、结果和未覆盖范围。

## 不建议的捷径

- 把所有用户网页当作 Hermes Dashboard 插件安装：这会强制依赖 Gateway/Profile，且当前插件脚本与宿主页面的隔离边界不足以承诺通用应用平台。
- 让应用网页自己启动服务进程：会绕开产品进程管理和退出回收。
- 接受任意 `localhost` 端口作为应用服务：可能误连用户或其他软件的进程。
- 一开始支持“任意源码自动构建并安装依赖”：各语言工具链、原生依赖和跨平台安装策略会显著扩大范围。首版接收可运行产物，开发工具链由作者选择。

实施前按仓库规则复核版本分支及已有改动。此文档仅是方案；代码、`ROADMAP.md` 状态和验收结果应在实际开发后分别更新。
