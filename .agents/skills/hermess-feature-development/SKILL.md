# Hermess 功能开发

本 Skill 适用于新增或修改产品功能，以及为实现该功能而进行的问题修复。它只指导功能从行为定义到实现和验证；分支、提交、ROADMAP、PR、CI、tag 和发布不属于本 Skill 的流程。仓库根目录及受影响目录的 `AGENTS.md` 始终适用，具体命令和约束以当前文件为准，不在此复制另一套规则。

## 定义功能与影响范围

1. 明确用户要完成的操作、入口、成功结果和可观察状态；按本次功能涉及的路径列出加载、空态、失败、重试、恢复、取消与切换行为。不为无关场景扩展需求。
2. 阅读当前生产实现、实际调用方、相关契约和已有验证。区分已确认事实与可能原因；用代码、日志、运行行为或可复现测试确认问题及影响范围。没有确认的问题先验证，不实施对应修复；证据不足时说明缺口，不因猜测增加兜底、兼容分支或额外状态。
3. 列出需要修改的模块、共享代码及可能受影响的现有功能。对共享样式、主题 token、全局 Provider、公共组件、构建入口或宿主装配的修改，逐项搜索所有生产消费者和独立入口，不能只检查当前页面。只实施目标功能及其必需依赖；发现范围需要扩大时，先说明依据和影响。
4. 修改前为本次可能受影响的历史行为建立基线证据。基线应来自当前生产装配后的可观察行为、计算结果或已有有效测试；不能把设计意图、局部源码值或未加载完整依赖的预览当作基线。

## 锁定行为变更边界

- 实现前写清本次“允许改变的行为”和“必须保持不变的行为”。允许改变项只来自用户明确要求及其不可缺少的依赖变化；未列入允许改变项的既有用户行为、视觉布局、交互状态、接口语义、持久化数据、配置、进程与资源边界默认全部保持不变。
- 修复缺陷时，只把已确认的错误行为改为目标行为；同一页面、共享组件或相邻流程中的其他行为仍属于保持不变项。重构、统一风格、复用公共代码或减少重复，都不构成改变其他功能的授权。
- 共享代码对非目标调用方必须保持行为等价。优先使用功能作用域、入口作用域或显式参数隔离变化；不得为实现一个入口的需求而修改所有消费者的默认行为。
- 实现或验证中发现范围外行为发生变化时，将其视为回归并修复或撤回相关改动，不得把它包装成顺便优化、合理统一或直接更新测试期望。若目标确实无法在不改变其他行为的情况下完成，停止扩大实现，列出证据、具体受影响行为和替代方案，取得用户明确确认后再把该变化加入允许改变项。

## 选择实现位置

- 实现前检查模块职责、数据与状态的所有者、依赖方向及现有调用路径。优先复用现有流程，以完成目标行为所需的最少层次和改动实现；抽取真正共享的逻辑，避免重复实现，也不为尚未出现的需求增加抽象。
- 检查方案在正常与异常路径上的复杂度、资源使用和响应表现。能以简单实现满足已确认的要求时，不引入额外状态、进程、轮询或多余的跨层往返；确有性能或规模问题时，以现有数据或可复现测量为依据调整。
- 前端组件、状态和用例逻辑留在所属 feature；宿主能力经 `@hermess/contracts` 注入。桌面 TypeScript 负责宿主适配与装配，Rust `main.rs` 负责初始化和注册，具体功能放在所属模块。共享契约只保存双方承诺的接口、类型和 Schema。
- 修改共享前端资源时先还原生产装配链：入口文件、静态与动态 import、样式加载顺序、选择器优先级、运行时属性或 Provider 初始化。尤其是新增或后加载的全局 CSS，不得覆盖目标范围外已有的布局、颜色、交互态；若需要覆盖，使用限定作用域并为原行为建立回归断言。源码中较早出现的正确规则不能证明最终页面仍采用该规则。
- 主窗口、独立聊天窗口、快捷输入窗、活动窗口和浏览器预览是不同入口。共享功能或主题改动必须核对实际引用它的每个生产入口是否完成相同的初始化和资源加载；不得从主窗口正常推断其他 WebView 正常。
- Windows 与 macOS 分别考虑实现与行为；共有业务逻辑复用，平台能力留在各自适配层。涉及产品进程、存储或路径时，遵守桌面和 Rust 目录规则，并保持与用户现有 Hermes 安装隔离。
- 产品功能优先在前端、契约和桌面适配层实现。锁定 Hermes fork 默认不改；若确有客户端无法适配的证据或升级原因，按根 `AGENTS.md` 的审批边界处理。
- 修改跨层接口前，逐项追踪生产调用、参数构造、契约、接收方校验、返回值与错误处理；Gateway 行为以锁定 fork 的对应入口为准。先查明原值和拟改值在接收方的实际语义，再调整实现。

## 让日志能定位功能运行结果

- 为一次功能操作建立可关联的日志上下文，使用现有的操作标识或关联机制；没有现成机制时，在功能范围内选用能串起该操作的稳定标识，不记录凭据、令牌、消息正文等敏感数据。
- 在有排查价值的节点记录操作开始、关键状态变化和最终结果。每条关键日志应能说明操作、所处节点和结果；失败、异常或超时要包含足以定位原因的非敏感上下文。涉及清理或回滚时，记录其执行结果。
- 从同一次操作的日志应能判断：关键节点依次完成且功能正常结束，或具体停在哪个节点、为何失败，以及清理是否完成。检查失败路径是否也有明确的终止结果，避免出现只有“开始”而无法判断后续状态的日志。
- 不为每个函数调用或高频事件机械增加日志；同一事实不重复记录。采用项目已有日志方式与级别，使正常路径和异常路径都可追踪。

## 验证功能

1. 验证目标功能的可观察行为，并回归受影响的现有入口和状态路径。测试输入在测试代码中构造，测试与生产代码按对应目录规则分开。
2. 按行为变更边界验收：允许改变项符合目标，直接受影响的保持不变项与修改前基线一致。任何范围外差异均判定为失败；除非先用生产证据证明旧测试本身不准确，否则不得通过修改历史断言或快照来接受差异。
3. 回归测试必须覆盖生产实际装配后的最终行为。测试夹具优先加载生产入口或与生产一致的完整 import 链；若夹具遗漏后加载的样式、Provider、初始化逻辑或独立窗口入口，或者自行重写被验证属性，它不能证明生产回归通过。无法复用生产装配时，列明差异并补充对真实入口的验证。
4. 共享视觉资源变更至少核对目标入口及其他消费者在代表性窗口宽度、明暗主题和关键交互态下的最终计算样式与可见结果。布局断言使用元素实际尺寸，主题断言使用最终颜色、背景和边框；截图用于目视复核，不能替代可失败的断言。
5. 按受影响目录运行当前仓库规定的检查。运行脚本前核对其输入、断言和生产调用是否一致；脚本通过只证明它实际覆盖的行为。
6. 修改 Gateway 请求时，用与当前 Rust 生产函数一致的请求形状，验证锁定 Gateway 对成功及关键拒绝用例的实际响应。本端类型检查、字符串断言、模拟 Gateway 或构建不能替代接收方验证；未通过时不得称该接口改动已完成。
7. 分别记录 Windows 与 macOS 已验证的行为、环境、方式、结果和未验证范围。区分浏览器预览、构建、Gateway 验证、原生窗口及安装包操作；不将一种验证写成另一种，也不将单平台结果写成双端通过。

完成时向用户说明实现的功能、确认过的行为、验证证据、仍未验证的场景及任何阻碍。仅报告本次实际完成的工作。
